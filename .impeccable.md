# Design Context

## Users

Research teams with mixed technical experience. Some users are comfortable with
CLI tools and JSON; others understand research governance but should not need to
know file formats or provider identifiers to start a run.

## Product character

Calm, precise, trustworthy, and concise. The CLI should explain the consequence
of a choice in plain English without weakening integrity controls or implying
that mechanical checks establish scientific correctness.

## First-use goal

A first-time user should be able to configure available providers and create a
valid H1-ready research run without editing JSON or memorizing `provider/model`
syntax. Each screen should end with one clear next action.

## Interaction model

- Use guided prompts by default only when stdin is a real terminal.
- Keep explicit flags and non-interactive paths stable for scripts and CI.
- Reveal advanced provider, model, effort, gate, and claim choices on demand.
- Accept numbers and familiar names in menus; never require internal syntax.
- Preview material writes and make cancellation safe.
- Keep human decisions terminal-only and attributable to a named person.

## Language

The public CLI remains in plain English. Wording should avoid unexplained jargon
and be short enough to scan in a terminal.
